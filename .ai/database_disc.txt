Podsumowanie Planowania Bazy Danych ClearMindHelper MVP
🎯 Główne Wymagania Schematu
ClearMindHelper wymaga schematu PostgreSQL (Supabase) obsługującego:

Multi-tenant data isolation (każdy użytkownik widzi tylko swoje dane)
Real-time BAC tracking z alert systemem
Complete audit trail dla edycji i zdarzeń (US-006, US-013)
Adaptive threshold system bazujący na historii urwań (US-014)
Historical data analysis dla przyszłych usprawnień algorytmu
📊 Kluczowe Encje i Relacje
Struktura Hierarchiczna:
Encje Kluczowe:
1. Users — Uwierzytelnianie

obsługiwane przez Supabase

2. UserProfiles — Dane do obliczeń BAC

user_id (FK), height_cm (INT, CHECK 50–250), weight_kg (DECIMAL, CHECK 30–300), gender (ENUM('M', 'F'))
profile_snapshot JSONB przechowywany w Parties dla każdej sesji (captured_at zawarte w JSONB)
3. Parties — Sesje imprezowe

user_id (FK), started_at (TIMESTAMP), ended_at (TIMESTAMP nullable), status (ENUM: 'ongoing', 'closed')
profile_snapshot (JSONB) — immutable snapshot {height_cm, weight_kg, gender, captured_at}
bac_estimate_max (DECIMAL 4,2), total_drinks_count (INT), total_ml_consumed (INT) — cache
blackout_marked (BOOLEAN), blackout_marked_at (TIMESTAMP nullable)
created_at, updated_at (TIMESTAMP)
4. Drinks — Wpisy napojów

party_id (FK), user_id (FK, denormalized), volume_ml (INT, CHECK > 0), abv_percent (DECIMAL 3,1, CHECK 0.1–100)
consumed_at (TIMESTAMP, w obrębie party time range)
original_values (JSONB nullable) — {volume_ml_before, abv_percent_before} jeśli edytowano
edited_at (TIMESTAMP nullable), edit_count (INT default 0)
order_sequence (INT) — ordinal position w party
5. BACCalculations — Historia szacowań BAC

party_id (FK), user_id (FK), drink_id (FK), calculated_bac (DECIMAL 4,2)
calculation_timestamp, algorithm_version (Widmark v1, etc.)
user_profile_snapshot (JSONB) — snapshot profilu w momencie kalkulacji
time_since_first_drink_minutes (INT), metabolized_alcohol_g (DECIMAL)

6. UserThresholds — Bieżące progi z historią

user_id (FK), threshold_bac (DECIMAL 4,2, default 0.160), is_current (BOOLEAN)
created_at, reason (ENUM: 'blackout_marked', 'manual_override')
trigger_party_id (FK nullable) — która impreza spowodowała zmianę (US-014)

7. Alerts — System alertów

party_id (FK), user_id (FK, denormalized), alert_type (ENUM: 'approaching_threshold', 'exceeded_threshold')
is_active (BOOLEAN) — True gdy user pozostaje powyżej progu
last_alert_sent_at (TIMESTAMP) — dla logiki powtarzania co 5 minut
bac_at_alert (DECIMAL 4,2), triggered_at (TIMESTAMP)
8. Events — Telemetria (US-013)

user_id (FK), party_id (FK nullable), event_type (ENUM: 'drink_added', 'drink_edited', 'party_started', 'party_closed', 'blackout_marked', 'threshold_adjusted')
created_at (TIMESTAMP)
⚠️ Bez event_data JSONB (per decyzja: minimalna telemetria)
⚠️ Sessions: obsługiwane przez Supabase Auth natywnie (auth.refresh_tokens), bez osobnej tabeli

🔄 Workflow Kluczowych Procesów
US-005: Dodawanie napoju
User dodaje napój (volume_ml, abv_percent, consumed_at)
Utwórz Drink record
Oblicz BAC (Widmark) dla nowego napoju
Utwórz BACCalculation
Sprawdź alerty:
BAC >= 0.90 * current_threshold → utwórz Alert (approaching)
BAC >= current_threshold → utwórz/update Alert (exceeded, is_active=true)
Log Event (event_type: 'drink_added')

US-014: Adaptacja progu po urwaniu
User zamyka party, ustawia blackout_marked = true
Backend queries peak_bac z BACCalculations
Utwórz nowy UserThreshold: threshold_bac = peak_bac, reason = 'blackout_marked', trigger_party_id = party_id, is_current = true
Aktualizuj poprzedni UserThreshold: is_current = false
Log Event (event_type: 'threshold_adjusted')

US-011: Powtarzające się alerty co 5 minut
Cron job co 5 minut uruchamia query: SELECT * FROM Alerts WHERE is_active = true AND last_alert_sent_at < NOW() - INTERVAL '5 minutes'
Dla każdego rekordu: wyślij powiadomienie UI
UPDATE Alerts SET last_alert_sent_at = NOW()
Gdy BAC spadnie (via next drink lub time-based decay), update Alert: is_active = false

US-006: Edycja ostatniego wpisu
User edytuje drink (ostatni w party)
Przechowaj original_values: {volume_ml_before, abv_percent_before}, ustaw edited_at, increment edit_count
Recalculate BAC dla tego napoju + wszystkie następne
Update all downstream BACCalculations
Re-check alerts (może się zmienić próg)
Log Event (event_type: 'drink_edited')

📋 Architektura Danych dla Historii (US-009)
Historia Imprez wyświetla:

Data startu/konca
bac_estimate_max (cached w Parties)
total_ml_consumed (cached)
Liczba napojów (total_drinks_count)
blackout_marked status
Szczegóły imprezy zawierają:

Lista Drinks (party_id) z timestamps, volumes, ABV
Lista BACCalculations (party_id) z calculated BAC values
original_values dla każdego edytowanego napoju (US-006 audit trail)
